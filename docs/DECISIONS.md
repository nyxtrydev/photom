# Decisions

1. **Tailwind v3** (not v4): stable config-driven token mapping.
2. **Fonts** via `@fontsource-variable/inter` and `/fraunces`, bundled by Vite, no remote loading.
3. **`--text-muted` darkened** to `#7A6757` (spec `#8A7767`) to meet WCAG AA on `--bg-app`.
4. **Extra `AppError` variants** `InvalidInput` and `Internal` beyond the spec list, for validation and unexpected failures.
5. **Plugins in Phase 0:** window-state, single-instance, store, dialog, fs, os. `updater` deferred to Phase 6 (needs signing keys; opt-in); `clipboard-manager` to Phase 4.
6. **Heavy crates deferred** (`ort`, `image`, `rayon`, ...) to the phase that uses them, to keep Phase 0 builds fast.
7. **Theme persistence** uses `localStorage` until the settings store lands (Phase 3).
8. **Title bar** is the same component across screens; the mockup editor menu bar slots in via `children`.
9. **Icons** generated from `docs/design/logo-source.png` with `tauri icon`; mobile icon sets removed (non-goal).
10. **Dev port 1430** (Tauri default 1420 clashes with other local Vite projects).
11. **`import_images` returns `{ images, rejected }`** instead of a bare `ImageMeta[]`, so one bad file never fails a whole import and the UI can explain each rejection.
12. **Fast model = ISNet general-use (Apache-2.0) with float16-stored weights, 90.6 MB** (the float32 original is 178.6 MB, over the 150 MB installer target). `scripts/make-fast-model.py` stores each large weight tensor as fp16 and adds a Cast back to fp32, so inference still runs in fp32: on the test photo the masks are identical (IoU 1.0000, mean difference 0.001/255) at the same speed. Photom prefers `isnet-general-use-fp16.onnx` and falls back to the fp32 file for developers; both are checksum-verified. Neither file is committed; `npm run model:fetch` downloads the fp32 file and builds the fp16 one when Python with `onnx` is available. Release builds must bundle only the fp16 file (Phase 6).
13. **`ort` 2.0.0-rc.13**, pinned. Windows/Linux/Apple Silicon use downloaded binaries. **Intel macOS has no prebuilt ONNX Runtime**, so it uses `load-dynamic` with a runtime 1.22.0 dylib in `src-tauri/vendor/` (dev only, git-ignored). Default graph-optimisation level is used because `Level3` needs a newer runtime.
14. **CUDA** is not wired yet (needs the `cuda` feature and separate binaries); DirectML covers Windows GPUs, CoreML covers Apple Silicon. Revisit in Phase 5.
15. **Mask transport** is a PNG file in the app cache dir (path returned over IPC), per Section 3.3.
16. **Dev profile** compiles dependencies at opt-level 3 and our crate at 1; image work is unusably slow otherwise.
17. **Hero illustration** is cropped from the mockup as a placeholder; replace `src/assets/illustrations/hero.png` with final art.
18. **CMYK TIFF** is not supported by the `image` crate; it is rejected with a Decode message. Revisit in Phase 5.
19. **Refine/edit maths runs in the frontend for preview** (`canvas/maskOps.ts`), not via `refine_mask`/`apply_mask_edit`/`compose_preview` IPC round-trips, to meet the 200 ms / 60 fps targets. The Rust exporter (Phase 4) re-implements the same maths at full resolution; the shared definitions are documented in `maskOps.ts` and covered by tests on both sides.
20. **Working size 2048**, not 2560: measured refine cost at 2560x1920 was ~140-260 ms on an Intel laptop CPU; 2048 keeps the default refine under the 200 ms target.
21. **Slider units** are source pixels (feather 0..20, edge shift -20..20, brush size 1..150) and scale with the working ratio.
22. **Plain wheel pans, Ctrl/Cmd+wheel zooms** (trackpad-friendly; pinch arrives as Ctrl+wheel).
23. **Home import opens the editor** with the first imported image; the interim "imported images" card list from Phase 1 was removed.
24. **Dev-only `window.__photom`** exposes stores to Playwright tests; it is compiled out of production builds (`import.meta.env.DEV`).
25. **Brush edits are stored as strokes in `state.json`**; no `mask_edits.png` in format v1 (strokes are authoritative and resolution-independent).
26. **Autosave links originals** instead of embedding them (fast, small), except originals that live in the app cache, which are embedded because the cache is not a stable location.
27. **Restored work is "unsaved"** and tied to the original path; Save overwrites the user's file only when the user asks. Opening a `.bak` after corruption never adopts the damaged file's path.
28. **Settings live in the backend** (Rust validates/migrates; the frontend mirrors). Theme is applied from `localStorage`-free settings after load; first paint uses the system theme.
29. **`window-state` plugin owns window geometry**, so `windowState` is not duplicated in `settings.json`.
30. **Model import** validates the file by creating an ONNX session, copies it atomically into `<app data>/models`, and verifies the checksum when the slot has a known hash. Nothing is ever downloaded by the app.
31. **Update check** button is present but disabled until the signed, opt-in updater ships in Phase 6.
32. **Export size semantics:** "Original" = size after the optional crop (never upscaled); "Custom" = exact W x H applied after cropping; presets may add a `maxSide` cap (Web = 2000 px).
33. **Crop box** uses mask values >= 10, so a feathered edge's faint halo counts as subject; the padding is exact relative to that box.
34. **Images without a cut-out** fail individually with a clear message instead of blocking a batch.
35. **Job events are triggers, snapshots are truth** (see ARCHITECTURE); this removes races between `export_png` returning the job id and the first events.
36. **Batch removal concurrency is 1** (the model session is shared); export concurrency is user-configurable 1-2 (`exportConcurrency`, no UI yet beyond defaults).
37. **Copy to clipboard** reuses the Export dialog's last-used options (current image, no file written).
38. **`success-fg` token** for success _text_ (4.5:1); `success` stays for dots/graphics (3:1). Dark `primary` lightened to `#dd7d44` so primary text on muted backgrounds passes AA.
39. **Menus are non-modal** (`modal={false}`): Radix's modal menus hide the rest of the page with `aria-hidden` while it stays focusable, which axe flags (`aria-hidden-focus`).
40. **Destructive confirmations:** unsaved changes, clear recent list, clear history, discard recovered work. Overwriting an existing project file is handled by the OS save dialog; exports never overwrite (auto-numbered), so there is no overwrite prompt.
41. **Toast actions close their toast**; errors never auto-dismiss.
42. **Quality (BiRefNet) model is wired but unvalidated:** no model file was available in this environment; its preprocessing constants and sigmoid come from the model's documentation. Test it with a real file before relying on it.
43. **`photom --smoke-test`** is part of the shipped binary (not a separate test harness) so CI can verify the exact packaged build: bundled model, ONNX Runtime library, file access. It writes its result to `--smoke-out` because Windows release builds have no console.
44. **The inference session is unloaded before exit** (`RunEvent::Exit`): tearing ONNX Runtime down while its thread pool is alive aborts the process (found by the smoke test).
45. **Release bundles ship only the fp16 model**, selected by `tauri.release.conf.json` (explicit resource list). Local/dev builds bundle whatever is in `resources/models`.
46. **Updater:** `tauri-plugin-updater` with a minisign key, `requireSignedVersion` on, no JS-side updater permission (all calls go through our own Rust commands), checks only on click. The committed public key is a development key; real releases must use their own (docs/RELEASING.md).
47. **Windows WebView2:** default installer downloads WebView2 only if missing; a separate `windows-offline` installer embeds it for machines that are never online.
48. **No git history exists in this working directory**, so changelog generation (`scripts/changelog.mjs`) and the release workflow were implemented and unit-tested but not run against real commits/tags here.
49. **`PHOTOM_MODELS_DIR`** adds a model search folder in any build (CI smoke tests use it for unbundled binaries). `PHOTOM_UPDATE_URL` overrides the update feed in **debug builds only**.

## Model Hub (Feature 0)

50. **Catalog host is a placeholder** (`models.photom.example`, `src-tauri/src/model_hub/config.rs`). Nothing contacts it in Phase H0. Catalog entries other than `bgremoval-fast` carry **all-zero placeholder hashes** and are reported `installable: false` until the real files are published and their licences re-checked. Sizes shown are estimates.
51. **Signed catalog, canonical JSON.** The signature covers the canonical form of the `models` array (keys sorted at every level, no whitespace, integers only). Rust (`manifest::canonical_json`) and Node (`scripts/lib/catalog.mjs`) are checked against the same test vector. Sign with `node scripts/sign-catalog.mjs <file>`.
52. **Development signing key.** The embedded public key belongs to `.keys/catalog-dev.pem` (git-ignored via `*.pem`). It must be replaced by a production key, held offline, before the first public release.
53. **A bad catalog is never fatal.** A catalog that is unsigned, tampered, wrongly signed or invalid is rejected; the bundled one is used and a warning is exposed through `model_catalog_status`.
54. **Requirements per feature** = the feature's `recommended` models plus their `dependsOn` closure. Optional models (x4 anime, AI denoise, Quality BG) never block a feature. Features that depend on one specific model (e.g. the upscaler by scale) use `check_models(ids)`.
55. **`ModelMissing` carries the model id** in its details, so the UI can show the install banner for that model.
56. **State = running work + registry.** Only running work (queued, downloading, paused, ...) is held in memory; `Installed`, `NotInstalled` and `UpdateAvailable` are derived from `registry.json`, the catalog and whether the file exists. Moving to a rest state ends the work and falls back to the derived state. Illegal jumps are refused.
57. **Existing background models are adopted, not migrated.** `bgremoval-fast` is derived from the bundled file (`source: bundled`, not removable); a user-imported or hand-placed BiRefNet file shows as `bgremoval-quality`, source `imported`, unverified. The old `ModelManager` still does the actual file lookup for background removal.
58. **Licences recorded for the planned catalog (to re-verify before publishing each file):** ISNet/DIS Apache-2.0, BiRefNet MIT, LaMa Apache-2.0, Real-ESRGAN BSD-3-Clause, NAFNet MIT, text detector Apache-2.0 (the exact detector is not chosen yet). None is non-commercial.
59. **Downloads happen only in Rust** (`reqwest` + rustls with the OS root certificates, system proxy). HTTPS only, host allowlist checked for the first URL and again for every redirect hop (max 5), connect/read timeouts. The web layer has no network permission and the CSP is unchanged.
60. **Retry policy:** per URL, 3 attempts with exponential backoff for transient errors (connection trouble, 429/5xx, truncated body); 4xx or a disallowed redirect skips straight to the next mirror. A mirror that fails or serves a corrupt file has its partial file deleted before the next mirror is tried, because bytes from different servers must not be spliced.
61. **Size is a hard cap:** a `Content-Length` or a body larger than the manifest size aborts the download and deletes the partial file.
62. **Resume:** `<models>/.downloads/<id>-<version>/<file>.part`, continued with `Range: bytes=N-`. A server that answers 200 (no range support) restarts from zero; a 206 at the wrong offset or a 416 discards the part and retries. Leftover staging folders at startup show as **Paused**. Verified, finished files in staging are re-verified and reused.
63. **Install is atomic:** verify (size + SHA-256) -> optional zip extraction -> `meta.json` -> rename the whole staging folder to `<models>/<id>/<version>` -> registry write (itself temp + rename) -> delete older version folders. Nothing half-installed is ever visible; `registry.json` is the switch.
64. **Multi-file and zip models:** a single-file model's `urls` are the file URL. For several files, each `urls` entry is a base folder and the file path is appended. `format: "zip"` downloads one archive (its hash is verified), extracts with path sanitising (no `..`, absolute paths or symlinks; entry count and expanded size capped, counted while reading) and expects `model.onnx` at the archive root.
65. **Disk space** is checked when a model is queued and again when it starts: remaining bytes (x2 for zip) plus a margin of 5% or 32 MB. Failure is `DiskFull` with the required and available MB.
66. **State additions:** `Verifying -> Downloading` is legal (next mirror or next file). Failures keep a code (`Network`, `DiskFull`, `HashMismatch`, ...) and also emit `model:error`. Pausing a running download only stops it; cancelling deletes its partial files.
67. **Catalog refresh** never errors the UI: offline, unsigned, tampered or older-than-current catalogs leave the current catalog in place and set a warning. A verified newer catalog is cached as `catalog.cache.json` and preferred at the next start when it is newer than the bundled one.
68. **Not yet in H1** (planned H3): install-many/recommended, import, remove, Advanced host/URL override. `model_open_folder` also waits for H3.
69. **Requirement logic lives in the store, not behind IPC.** `useModelRequirement` computes "what does this feature need" from the model list already in `hubStore` (recommended models of the feature plus their dependency closure, the same rule as `ModelHub::required_for_feature`), so panels unlock the instant a `model:state` event arrives. `model_check_requirements` stays as the backend's own check for services. Progress is summed over _all_ required models so the bar never jumps back when one of two finishes.
70. **The banner is mounted in the existing Settings > Background removal tab** (for `bgremoval-quality`) because the Text Removal, Upscale and Enhance panels do not exist yet. Those features mount `<ModelInstallBanner requirement={{ feature }} />` and wrap their controls in `<ModelGate>` (a disabled `fieldset` with a tooltip). Hub-installed Quality models are found by background removal through `AppState::locate_model`.
71. **Settings tabs:** the old "Model" tab is now **Background removal** (engine choice, CPU/GPU); the new **Models** tab is the hub (list, install, pause, resume, cancel, details). Install/Update/Retry and the header actions (install recommended, install all, check for updates, open folder) are there; remove and import arrive in H3.
72. **First-run offer** (`ModelsWelcomeDialog`) appears only on the empty Home screen, only when at least one recommended model can actually be downloaded, never over another dialog, and is recorded in `modelsOnboardingDone` (Esc = skip). Settings > Models has "Show the first-run offer again". With today's placeholder catalog nothing is downloadable, so it does not appear.
73. **Licence URLs are shown as text, not links:** the webview must never navigate away from the app and there is no opener plugin (least privilege).
74. **"... is ready" toast** fires once per finished install, for the feature when the model belongs to its required set and everything else it needs is there, otherwise for the model by name. Its Open action uses `registerFeatureOpener(feature, fn)`; features register themselves, and the default opens the Models page.
75. **Download chip** sits in the footer of the home screens and in the editor status bar, shows the active model with a percentage and "+N more", and opens the Models page.
76. **Import (`model_import_file`)** works for single-file, non-zip models. The file's SHA-256 and size are compared with the catalog; a match installs it as **verified**, anything else (including every model whose catalog hash is still a placeholder) is refused with the `Unverified` error _before any state changes_ and only installed after the UI asks and the user chooses "I understand this file is unverified" (`allowUnverified: true`). It is then recorded `source: imported, verified: false` and shown with an **Unverified file** badge, also after a restart. The copy is hashed while it is written, so what is installed is what was checked. The user's original file is never moved or deleted.
77. **Remove (`model_remove`)**: state `Removing`, then every holder of a session is told to let go (`ModelHub::invalidate`), then the registry entry and `<models>/<id>/` are deleted, then `NotInstalled`. Unload-before-delete matters on Windows, where a mapped file cannot be deleted. Bundled models are refused (`Permission`); busy models (queued, downloading, ...) are refused until cancelled.
78. **Session cache** (`session_cache.rs`): one `Arc<Mutex<Session>>` per model, keyed by installed version plus a variant (device preference). A new version or device replaces it; `ModelHub::add_unload_hook` evicts it on removal, import and update (the update hook runs after the registry switch and before the old version folder is deleted). A missing model is `ModelMissing` carrying its id. `open_session` is shared with the background-removal engine, which is unloaded by the same hook when its model is removed or replaced. Sessions are cleared before exit (decision 44).
79. **Advanced settings:** `modelsCatalogUrl` (https only, no credentials) and `modelsExtraHost` (a bare host name) are validated in Rust, applied immediately (the HTTP client is rebuilt) and at startup. The catalog URL's host is allowed automatically because the user chose it; the extra host is the only other addition to the allowlist. This does not weaken verification: a catalog must still carry a valid signature and every file must match its hash. Proxy: the system proxy is used automatically; there is no separate proxy field.
80. **Per-model import, no global "Import model file" button.** Importing needs to know which model it is for, so each row has **Import file**, and a failed offline install offers **Import a file** in the banner, which opens the Models page. The folder button opens the models folder.
81. **End-to-end proof of offline use:** a Rust test installs a real (hand-encoded `Identity`) ONNX model through the whole pipeline (signed catalog, download, verify, atomic install), runs it through the session cache, then drops the server, restarts the hub with unreachable URLs and runs it again. Another test asserts that starting up, listing models and checking requirements send no requests, and that a leftover partial download comes back as Paused instead of resuming by itself.
82. **Security guards are tests** (`src/tests/security.rs`): the CSP's `connect-src` may only contain `'self'` and the IPC origins, the window capability may not include http/shell/opener/fs/updater permissions, no http/shell/opener plugin may be linked, and model files may not be in the asset-protocol scope. The bundled catalog is also checked for permissive commercial licences, allowed hosts and attribution.
83. **Keyboard focus follows a changing banner or row** (`useKeepFocus`): when Install now is swapped for Pause, focus moves to the new button only if it was inside the component and has been lost; deliberate moves elsewhere are respected.
84. **Publishing tools:** `scripts/catalog-fill.mjs` fills hash and size from a real file, `scripts/sign-catalog.mjs` signs; `docs/MODEL_HUB.md` has the publishing checklist and key rotation notes.

## Shadow Generator (Feature 2)

85. **Phase S0 scope:** the Shadow tab, data model, drop-shadow layer with a live canvas preview, automatic canvas expansion, undo/redo, save/open and the v2 project format. Contact, cast and reflection layers, the ground line, presets, "Shadow only", export integration and batch are later phases (S1-S3). The Rust side has the parameter validation and canvas-bounds maths now (`services/shadow.rs`); the full-resolution renderer arrives with export in S2.
86. **Units and direction:** distance, blur and spread are in source pixels; blur is a Gaussian with sigma = blur / 2; angle is the _light_ direction (135 = from the upper left, so the shadow falls lower right; y is down). With a preset applied to images of different sizes, fixed pixels will look inconsistent; S3 will decide whether presets scale with image size.
87. **The editing frame:** the image stays at source (0,0); the canvas "frame" is the image plus the margin a shadow needs, so brush strokes, zoom and saved coordinates are unaffected. It is derived from the mask and shadow (never saved), grows only for visible layers with opacity > 0, is rounded outward and capped at one image size per side. The view re-fits when the frame changes (not while a slider is still being dragged) and the Before/After divider spans the frame.
88. **Preview is computed on a proxy** (longest side 640 px; the subject's box comes from a 256 px coarse mask cached per mask revision) and cached per (mask revision, settings), so panning costs nothing. It reuses the mask blur and morphology code, so the blur matches the rest of the editor. Layers composite bottom to top (list order) with straight-alpha "over".
89. **One undo step per drag:** slider changes update live and `commitShadow` records a single step; enable, add, hide, delete, auto-expand and reset are their own steps and first close any drag in progress. Undoing the first enable returns the shadow to `null` ("never configured").
90. **Format 2:** `FORMAT_VERSION` is now 2; the v1 -> v2 migration only changes the version number because a missing `shadow` already means none. Older apps refuse v2 files with the existing "newer version" message. `shadow` is also part of what marks a project as modified (and so triggers autosave and the unsaved-changes prompt).
91. **Properties panel tabs:** the panel now has a tab strip (Background | Shadow) so later features can add Enhance, Upscale and Text Removal. The Background tab holds the previous sections unchanged.

### Phase S1: contact and cast shadows

92. **Scope of S1:** contact and cast layers, the ground line (automatic or manual) with an on-canvas handle, one light-direction handle, and layer reordering. Reflection, presets, "Shadow only", export and batch stay in S2/S3. The Rust side gains the parameter parsing and canvas-bounds maths for the new layers (shared fixture, 9 new cases); the pixel renderer is still TypeScript-only until S2.
93. **Ground line:** `groundY` is a fraction of the image height; `null` means the subject's lowest pixel with alpha above 8/255 (read from the 640 px proxy, so the preview is accurate to about one proxy pixel; the export will measure at full resolution). Contact and cast shadows hang from it; the drop shadow ignores it.
94. **Contact shadow:** the `size` px of the subject just above the ground line are flattened to 25% of their height and laid just below the line (shifted by `groundOffset`), weighted 1 at the line to 0 at `size` above it, then blurred by `softness`. Because the subject is drawn over it, only the part below the ground line shows, which is what reads as "touching the floor".
95. **Cast shadow:** a pixel `h` above the ground line lands at `(x + sx*h, ground + sy*h)` where `(sx, sy) = L * (-cos a, sin a * squash)` and `L = min(6, length / tan(elevation))`. Rows are drawn forward in sub-steps (about one per pixel of travel) so steep or long projections stay solid; overlaps keep the maximum, so thin parts such as a pole do not break up. Opacity falls linearly to `1 - falloff` at the top of the subject.
96. **Blur that grows with distance:** the cast shadow is rendered into four planes with blur from `blur` to `blur + blurGrowth`; each row feeds the two planes either side of its distance along the shadow (weights sum to 1) and the planes are blurred and summed. Four levels is the smallest count with no visible banding on the test shapes; it costs four blurs of the frame.
97. **One light:** the canvas light handle sets the angle of every drop and cast layer together (contact shadows have no direction). The angle sliders stay per layer, so lighting can still be made deliberately inconsistent. Handles are shown only while the Shadow tab is open and "Show ground line and light handles" is on; both are keyboard operable (arrows, Shift = bigger steps) and a drag is one undo step.
98. **Reordering** is by Move up / Move down buttons (always keyboard accessible); each move is one undo step. List order is draw order, bottom to top.
99. **Format stays at 2:** new layer types only add data, and older S0 builds already skip unknown layer types, so no migration or version bump is needed.
100.  **Bounds for new layers:** contact = subject width, from the ground line (plus offset) down by `size * 0.25`; cast = subject width plus the full shadow vector from the ground line; both grown by three sigma of their largest blur. Capped at one image size per side like the drop shadow.

### Phase S2: reflection, presets and export

101. **Scope of S2:** reflection layer, four built-in and custom presets, the "Shadow only" view, Export dialog options, and the full-resolution Rust renderer. Batch "Apply to all" and rayon tuning stay in S3.
102. **Reflection** is the only layer that uses the subject's colours (not a tint): the rows within `fade` px above the ground line are flipped about it, moved down by `gap`, faded linearly to nothing, and blurred. Colours are blurred premultiplied (four planes) so edges do not pick up dark fringes. It has no colour field; opacity, gap, fade length and blur are its controls.
103. **One renderer, two languages:** `shadow_render.rs` is a line-for-line port of `renderShadow`, using the same integer blur and morphology (`maskops`) and JavaScript's rounding rule. `tests/fixtures/shadow_render.json` holds five cases (every layer type, plus a stack with a manual ground line) with the bytes the editor draws; Rust must land within one level of them (float rounding is the only difference). Regenerate with `UPDATE_SHADOW_FIXTURE=1 npx vitest run src/canvas/shadow.test.ts`.
104. **Export pipeline:** the shadow is drawn from the _final_ full-resolution alpha (after refine and brush edits), the frame comes from `ShadowParams::bounds`, and the subject is composited over it before cropping and resizing. So "Crop to subject" keeps the shadow (the crop box is the union of subject and shadow), and a custom output size scales both together.
105. **Include shadow / Shadow on separate layer:** "Include shadow" (default on) bakes the shadow into the picture; "Shadow on separate layer" additionally writes `name-photom-shadow.png`, the same size and crop, shadow only, never given the background. The two are independent: designers turn Include off and the layer on, and the main picture then keeps the same enlarged canvas so the two files line up. If neither is wanted the export is byte-for-byte what it was before shadows existed. The dialog only shows these options when an image in scope has a shadow enabled.
106. **Presets scale with the image.** Stored values are for a 1500 px longest side and are multiplied by `longestSide / 1500` when applied (distance, blur, spread, size, softness, offsets, fade, gap), so a preset looks the same on a 1000 px and a 6000 px photo (this settles decision 86). Angles, opacities and colours do not scale. Applying a preset keeps the image's own ground line, replaces all layers in one undo step, and re-clamps every value, so an edited preset cannot exceed the limits. Any later edit switches the chip row to "Custom".
107. **Custom presets live in settings** (`shadowPresets`, at most 30, names up to 60 characters, validated by `commands::shadow` by parsing the layers like a project file). Built-in presets cannot be renamed or deleted. `shadow_presets_list/save/delete` are the three IPC commands from the spec.
108. **Shadow only** is a view setting like Before/After: not saved, not an undo step. It draws the shadow alone on a neutral grey (`#d4d4d4`) with no subject, background or split.
109. **Memory guard:** a shadow canvas larger than 160 MP is refused with a clear message (reduce the shadow or turn off Auto expand) instead of exhausting memory.
110. **Full-resolution time is over budget with all layer types:** a 12 MP image with a drop shadow renders in about 0.4 s, but a stack of reflection + drop + contact + cast (four blur levels, four reflection planes) on the resulting 18 MP canvas takes about 3.8 s against the 2 s target. It is correct but not yet fast; parallelising the blurs and restricting them to the area the layer actually covers is Phase S3's profiling work.

### Phase S3: batch, speed and polish

111. **Apply to all images** copies the active image's shadow layers to every other image that has a cut-out, as a job in the existing queue (`shadow_apply_batch`, kind `applyShadow`): progress dialog, pause/cancel, per-image errors, Retry failed. Each image's copy is scaled to its own size with the preset maths (decision 106), so 40 images of different sizes get the same look; ground lines are re-detected per image; images without a cut-out are skipped with a notice.
112. **What the job does:** the shadow itself is only settings, so the backend job validates each image at full resolution (final alpha after refine and brush edits, subject found, shadow canvas renderable under the 160 MP limit) and returns the canvas it would need. The editor adopts the shadow for an image only when its check passed, as one undo step per image, whether the result arrives as an item event or in the final summary (idempotent). Failed images keep what they had.
113. **History:** a finished batch adds one History entry ("Shadow: grounded applied to 38 images") rather than one per image. It is written when the last image is processed, so a cancelled batch leaves no entry.
114. **Speed:** the blur levels of a cast shadow, the four planes of a reflection, the layer compositing and the final conversion run on rayon threads. On the 12 MP worst case (reflection + drop + contact + cast, 18 MP canvas) the render went from 3.8 s to 1.7 s; drop-only is 0.3 s. The vertical box-blur pass is still single-threaded (it sweeps rows with running totals).
115. **Linear light** is a per-image shadow option ("Blend layers in linear light", off by default, saved with the project and carried by presets/Apply to all). It changes how layer _colours_ mix where layers of different colours overlap; it is part of the shared renderer so preview and export agree. It deliberately does not change how the finished shadow is blended with the subject and background: the editor's 2D canvas cannot do that in linear light, and an export that differed from the preview would be worse than the small inaccuracy.
116. **Dither:** the shadow's alpha is quantised with a 4 x 4 ordered (Bayer) dither: `floor(alpha * 255 + t)` with t between 1/32 and 31/32. It keeps the average (a flat 30 % shadow alternates 76 and 77 instead of banding) and leaves fully clear and fully solid pixels alone. The table is identical in both renderers; the pattern is tied to frame pixels, so the preview (a proxy) and the export differ in pattern but not in average.
117. **Accessibility and themes:** axe audits (light and dark) cover the Shadow tab with presets, handles, naming a preset, the Shadow-only view and the Export dialog with shadow options. A test confirms the canvas shadow is pixel-identical in both themes (canvas colours do not follow the UI theme).

### Phase S4: tests

118. **Golden pictures** (`src-tauri/tests/golden/*.png`, 5 files, 240 px): a bottle, a shoe and a chair (thin legs) stand-in rendered through the real export pipeline (`exporter::render`: final alpha, shadow, composite, background) with the Product, Grounded and Soft studio looks, a transparent-canvas chair, and a linear-light two-colour bottle. Compared with a tolerance of 3 levels per channel and a mean of 0.1, which absorbs cross-platform float differences but not a visible change. Regenerate with `UPDATE_GOLDEN=1 cargo test --lib golden` and review the PNGs before committing. The subjects are synthetic shapes, so they prove the pipeline is stable, not that shadows look good on real photographs.

## Image Upscaler (Feature 3)

### Phase U0: shell, estimate and the no-AI upscaler

121. **Scope of U0:** the Upscale tab, Home sidebar entry, scale and custom-target controls, backend estimate, model-banner wiring, the Standard (no AI) upscaler, Before/After review with a 100 % detail view, Keep/Discard, project storage (format 3). Tiling, model inference, alpha options, pre-denoise, export size and shadow/brush interaction are U1/U2. AI is shown in the Method list but disabled with "not available in this build yet"; `upscale_run` refuses it with the same message.
122. **One place decides the output size:** `services/upscale.rs::output_size` is used by both the estimate and the upscaler, so they cannot disagree (a test runs every kind of request through both). A scale is 2x or 4x; a target must be larger than the image in at least one side; the longest side is limited to 32768 px.
123. **Estimate:** output size, megapixels, seconds and memory, plus warnings with stable codes. Blocking: result over the cap (`pixel limit` setting, default 100 MP) or a side over 32768. Notices: result over half the cap, input already large (3000 px or 8 MP), input very small (under 64 px). The seconds constant (0.07 s per output MP) comes from a measured 1 MP to 16 MP run (0.87 s); transparent images are slower than the estimate.
124. **Standard upscaler:** Lanczos3 then a mild unsharp mask (sigma 1.0, amount 0.4). Transparent images resize colour and alpha separately: clear pixels first take their visible neighbours' colour for four rings, so no hidden colour bleeds into edges and no division by a tiny alpha is needed. Pixels fainter than 32/255 are not sharpened. Tests catch the two failures this design replaced: 8-bit premultiplication left garbage colour at alpha 5, and sharpening next to clear pixels overshot to white.
125. **Result lifecycle:** `upscale_run` is a one-item job. The result waits in the store (`cache/upscale/<id>/pending-*.png`) until Keep (`kept_2x.png`/`kept_custom.png`, recorded in the image registry) or Discard. Discarding a result under review keeps an earlier kept version (`include_kept: false`); "Back to the original" removes it. A new unreviewed result replaces and deletes the previous one. Cancel returns to the panel immediately; the queue lets the running item finish (decision on cancel semantics), and the late result is deleted when it arrives.
126. **Keep is not an undo step:** it creates or deletes a file. It does mark the project as changed.
127. **Project format 3:** a kept upscale is stored as `images/<id>/upscaled_2x.png`, `upscaled_4x.png` or `upscaled_custom.png`, listed in the manifest (`upscaled: {file, width, height, scale, engine}`), with its parameters also in `state.json` (`upscale`). The file is the truth on open: parameters without a picture are ignored. Format 1 and 2 projects open with no upscale. Autosaves carry it too.
128. **Review view:** while a result waits, the canvas is replaced by a Before/After comparison (the working preview of the original against the result decoded to at most 2048 px) with a keyboard-operable divider. The 100 % detail view does not use the screen pixels: the backend crops the real result and the matching bilinear-enlarged original (`upscale_loupe`, 128 px square each) as the pointer moves, one request at a time.
129. **Model banner:** shown for the model of the chosen scale (`upscale-x2` or `upscale-x4`; a custom target that needs more than 2x uses x4), as the spec asks. Installing it does nothing visible until U1, which is stated in the phase report.
130. **History:** keeping an upscale adds a History entry ("photo.jpg upscaled to 3200 x 2400").

### Phase U1: AI upscaling by tiles

131. **Tiling (`services/upscale_ai.rs`):** the model takes a fixed 256 x 256 tile (catalog `inputSize`). The image gets an 8 px mirror pad all round (so its borders have context), then tiles overlap by 16 input pixels; the last tile in a row is clamped to end at the edge. Images smaller than a tile are mirror-padded to one tile and cropped back.
132. **Blending:** each upscaled tile is weighted by a ramp (never zero) over its overlap on sides that have a neighbour and flat 1 on image edges; weighted sums are divided by the weight total. The tiling takes the model as a closure, so tests use a nearest-neighbour stand-in whose exact answer is known: a 600 x 300 image through 20+ tiles matches a plain enlargement within 1/255 (no seams), and small and 1 x 1 images work.
133. **Transparency in U1:** the model only sees colour (clear pixels take neighbour colour first, as for Standard); alpha is resized separately and put back. Proper alpha options are U2.
134. **Custom targets:** the model runs at the smallest of 2x/4x that covers the target, then Lanczos resizes to the exact size, so the estimate's size is always the output size.
135. **Cancel:** `upscale_cancel` sets a per-image flag the tile loop checks before every tile, so Cancel stops within one tile (about a second or two on a CPU) instead of waiting for the whole image; the item ends as `Cancelled`, which the UI does not show as an error. Progress is the `upscale:progress` event (tiles done of total).
136. **Memory guard:** the AI estimate counts the f32 accumulators (16 B per model-scale pixel) plus the RGBA copies. Before running, the need is compared with the memory the machine reports (Linux `MemAvailable`; macOS total memory; unknown on Windows, where only the pixel limit applies) and a run needing more than 80 % is refused with an `OutOfMemory` message. The time estimate for AI is 1.5 s per tile (unmeasured CPU guess).
137. **Model use:** the session comes from the Model Hub's shared cache (`upscale-x2` / `upscale-x4`, CPU for now; GPU is U3). Standard needs no model, so the install banner appears only once AI is chosen, and Upscale stays disabled until the model is installed.

### Phase U2: bundled models, pipeline integration and options

138. **The upscaler models ship inside the app.** `upscale-x2` and `upscale-x4` are `realesrgan-x2.onnx` and `realesrgan-x4.onnx` (67 MB each, fp32, in `resources/models/`), catalog entries with no download URL, real hashes and a re-signed bundled catalog. The Model Hub treats a catalog model with no URL as installed when its file is next to the other bundled models (`ModelManager::locate_file`, `Hub::shipped_record`). Source and licence check: exported 1:1 from the official `RealESRGAN_x2plus` / `x4plus` weights (xinntao/Real-ESRGAN, BSD-3-Clause), published as `SceneWorks/real-esrgan-onnx` on Hugging Face (BSD-3-Clause on the model card); sha256 `7115ba92...9002c` (x2) and `5c586662...b89c033` (x4) match the card; both take any input size. The user asked for them to ship. The fp32 files add 134 MB to the installer; halving it with the fp16 script is possible but not done (needs the Python `onnx` package).
139. **No anime model.** `upscale-x4-anime` was removed from the catalog (no ONNX build was found; the user dropped it). The catalog has 7 models.
140. **Tested with the real models:** a 300 x 270 picture through 4 tiles matches the model run on the whole picture at 50.5 dB (2x) and 45.4 dB (4x), and Lanczos at 33.7 and 32.0 dB: no seams, and the output is the picture. Measured on a loaded Apple-silicon Mac, CPU only: 3.7 s per tile at 2x, 12 s per tile at 4x. The AI time estimate is now `tiles * 0.8 * scale^2` seconds.
141. **A kept upscale replaces the picture the export works on.** `upscale::with_kept` swaps the record's source for the kept PNG and sets `ItemState.detail_scale` (kept width / original width; set by the backend only, never read from the editor). The editor keeps working on the original preview; export and copy-to-clipboard render from the upscaled picture. The mask is resized to it by the existing edge-aware resize.
142. **Everything in original pixels scales with it:** feather and edge shift go through the `scale` argument `compute_refined` already had, brush strokes through `replay_strokes`'s, and the shadow through `shadow_render::render`'s: the shadow settings stay in original pixels, the subject is found in the upscaled alpha and converted back, and the frame is converted forward again (`shadow_layout`). With no upscale (scale 1) the arithmetic is the identity, so existing output and the golden images are unchanged. A test renders the same state at 2x and 4x and compares it with the original rendering enlarged (mean difference under 4/255); another checks that ignoring the scale would change the picture.
143. **Output size:** with "Original" size the export is the upscaled size. A size the user typed in Output is honoured as typed. The Output section and status bar say that the upscaled picture is used.
144. **Reduce artefacts** (pre-denoise): a 3x3 bilateral filter (spatial sigma 1, range sigma 18) on colour only, alpha untouched, before either engine. Off by default.
145. **Alpha:** colour and alpha are processed separately for both engines (decisions 124, 133). The extra "threshold and feather" clean-up of the alpha edge in the spec is not done; the Lanczos-resized alpha is used as is.
146. **Not done in U2:** the editor canvas still shows the original-size preview; the Export dialog's own size fields show the original size even though "Original" exports the upscaled one.

### Phase U3: batch, GPU, size cap, polish

147. **Batch upscaling (`upscale_batch`):** one job of kind `upscaleBatch`, one image at a time (the model already uses every core). Same scale, method and options for every image; a custom target size is refused (it belongs to one image). Each result is kept as soon as it is made (decision: batch is "set and forget"; "Back to the original" in the Upscale tab undoes one image) and gets its own History entry. A failing image only fails itself; Retry runs the failed ones again with the same settings. The AI engine needs its model installed before the batch starts (`ModelMissing` otherwise).
148. **Cancel in a batch:** the queue stops after the current image; the front end also flags every image so the one being upscaled stops at its next tile (the flag is cleared when an image starts, so a stale one cannot stop a later run).
149. **Size cap setting:** `upscaleMaxMp` (default 100, 1 to 1000), separate from the decode limit `pixelLimitMp`, in Settings > General. The estimate and the run both read it; a result over it is blocked with an explanation.
150. **GPU:** the AI engine follows Settings > Model (CPU, or GPU if available): the session cache keeps one session per device choice, and `open_session` falls back to the CPU when no provider exists (this Intel Mac has none, so only the fallback was exercised here; DirectML on Windows and CoreML on Apple silicon are untested).
151. **Speed target not met on CPU:** the spec asks for about 20 to 40 s for 1 MP at 4x. The x4 model on this loaded Intel Mac needs 9 to 12 s per 256 px tile and a 1 MP image has about 25 tiles, so 2 to 5 minutes; 2x is about a quarter of that. The estimate says so before the run. A GPU, a quiet machine or a lighter model would be needed for the target; the UI stays responsive and cancel works within a tile.
